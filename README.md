# cachequery — 有限查询语言 + 分层复用缓存 + 失效传播

分析查询常常只改一个筛选或时间范围。本项目实现一个**有限查询语言**及其执行引擎,
把计算结果缓存在**三个层次**,每次复用都必须附带**可展示的证明条件**;
证明不了等价就真实重算。数据更正、权限收窄、口径升级都会使部分缓存失效,
失效沿依赖登记传播,并发查询通过纪元校验保证不漏。

纯 Python 3 标准库,零依赖。

## 快速开始

```bash
python3 -m cachequery.demo        # 命令行演示:四个样例 + 基准 + 并发 + 中断恢复
python3 -m unittest discover -s tests   # 26 个测试
python3 -m cachequery.server 8000       # 网页: http://127.0.0.1:8000/
```

## 查询语言

```sql
SELECT sum(amount), avg(amount), count_distinct(user_id)
FROM events
WHERE country = 'CN' AND date >= '2026-01-01' AND date < '2026-02-01'
      AND channel IN ('web','app') AND amount IS NOT NULL
GROUP BY country, channel
```

- 聚合:`sum` / `avg` / `count_distinct`
- 条件:`= != < <= > >= IN(...) IS NULL / IS NOT NULL`,仅以 `AND` 连接
- 规范化:条件/度量/分组排序去重、字面量在左自动翻转 → `a=1 AND b=2` 与 `b=2 AND a=1` 同键
- 空值语义(SQL 风格):除 `IS NULL` 外,任何涉及 NULL 的比较为假;
  `avg`/`sum` 跳过 NULL 金额,`count_distinct` 跳过 NULL 用户,`GROUP BY` 保留 NULL 组

## 三个缓存层次:空间 vs 计算

| 层次 | 内容 | 复用条件(证明) | 空间 | 节省的计算 |
|---|---|---|---|---|
| **L1 原始分片** | 某分区某筛选下的明细行 | 同分区 + 数据版本一致 + **行集包含证明**(查询筛选+权限 ⇒ 分片筛选),取回后**重新过滤** | 最大(行的复制) | 跳过原始扫描,可在包含关系下复用 |
| **L2 可组合状态** | 某分区某筛选某分组下的 `(Σ分,计数)` 与去重集合 | 筛选完全一致 + 权限一致 + 数据/口径版本一致;**分组更细可上卷**(投影);**跨分区可合并**(和相加、计数相加、集合求并) | 小(每组几十字节) | 免扫描免聚合,是「只改时间范围」复用的主力 |
| **L3 最终结果** | 整个查询的最终行 | 规范化查询**完全相同** + 权限一致 + 全部资源版本一致 | 最小 | 直接返回 |

实测(基准负载,见网页 ④⑦ 面板):L1 ≈ 20 KB/条,L2 ≈ 0.4 KB/条,L3 ≈ 0.1 KB/条;
热遍查询 0 行扫描、亚毫秒返回。

**关键设计:范围包含 ≠ 聚合可复用。** 查询范围被某 L3 结果包含时,
`sum/avg/count_distinct` 都**无法**从超集结果中扣除,因此拒绝复用 L3
(页面「拒绝复用」栏会显示该证明失败原因),改由按日 L2 状态重组;
而 L1 原始分片在同样的包含关系下**可以**复用——因为拿回来的是行,会再过滤。
去重人数用精确集合作可组合状态(可并集);若改用 HLL 等近似 sketch 可进一步省空间,
但将失去与基线逐位一致的特性,本项目不采用。

金额一律以「分」(整数)累计,保证分片合并结果与一次性全量计算**逐位相等**。

## 失效传播(依赖登记)

每个条目登记两类依赖,失效沿两者传播:

- **资源版本**:`data:<分区日>`、`semantics`(口径)、`perm`(权限纪元)。
  资源升级时,所有记录旧版本的条目失效;
- **条目依赖**(deps):L3 依赖构建时使用的 L2,L2 依赖来源 L1。上游失效级联下游。

三类失效源:

1. **数据更正** → `data:<日>` 版本 +1 → 该日 L1/L2 与依赖它们的 L3 失效,
   其余分区缓存继续复用(部分失效);
2. **权限收窄** → 用户级收窄:L2/L3 键含范围指纹,自然失配重算;L1 满足包含证明仍可复用。
   全局限制某国家:含该国家的条目被主动逐出,ALL 范围用户的有效范围自动收缩;
3. **口径升级**(同形不同含义)→ `semantics` 版本 +1 → L2/L3 全部失效,
   L1 原始分片与口径无关**保留**(部分失效)。

**并发不漏**:所有缓存读写与失效在同一把锁上完成;执行器计算前读失效纪元 epoch,
组装后在锁内逐一校验所用条目与资源版本,任何中途发生的失效都会导致丢弃重试
(有界重试后在全局锁内完成,保证终止)。`tests` 中 6 线程查询 × 40 次并发更正
做 epoch 夹逼断言:窗口无失效则缓存结果必须逐行等于基线。

## 中断恢复

条目两阶段构建:`building`(先落盘)→ `complete`(原子替换提交)。
崩溃模拟在 building 落盘后触发;重启时 `recover()` 丢弃全部 building 半成品,
后续查询按需重建。持久化节流 100ms,失效/恢复/崩溃演示路径强制同步写
(丢失的 commit 落盘在恢复时表现为 building 被丢弃,只是少一条缓存,结果不变)。

## 样例(网页 ③ 一键运行 / `python3 -m cachequery.demo`)

1. **同形不同含义**:同一条 SQL,口径 v1(毛额/全部用户)与 v2(净额/活跃用户)
   结果不同,缓存按键隔离,升级后旧条目不可复用;
2. **空值**:NULL 国家/金额/用户的聚合与分组行为,缓存结果与基线一致;
3. **跨版本**:更正单日数据 → 该日重算、其余四日 L2 复用、L3 级联失效;
4. **范围包含误用**:整月结果缓存在,子范围查询被拒绝套用,改走 L2 重组。

## 目录结构

```
cachequery/
  querylang.py   词法/语法/规范化/行匹配/筛选蕴含证明/分区裁剪
  data.py        数据集(按日分区、含空值)、数据版本、更正
  cache.py       缓存存储:依赖登记、失效级联、持久化、恢复、epoch
  executor.py    执行器:L1/L2/L3 构建与复用、证明生成、并发校验、基线
  samples.py     四个样例 + 基准对比 + 并发压力 + 恢复检查
  server.py      HTTP API + 单页网页
  demo.py        命令行演示
tests/test_cachequery.py   26 个测试
```
